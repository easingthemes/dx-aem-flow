<SectionHeading
  badge="Skills"
  badgeColor="secondary"
  title="Skill Authoring"
  subtitle="YAML frontmatter + markdown body = a reusable command."
  bg="primary"
/>
<Section>
  <CommandBlock label="Complete skill frontmatter">{`---
name: my-skill                    # Required. Becomes /plugin:my-skill command
description: What it does...      # Required. Used for auto-invocation matching
argument-hint: "<expected args>"  # Optional. UI placeholder text
context: fork                     # Optional. "fork" = isolated subagent execution
agent: my-agent                   # Optional. Agent for the fork
model: sonnet                     # Optional. opus | sonnet | haiku -- never a pinned id
effort: high                      # Optional. low | medium | high | xhigh
paths: ["**/*.ts"]                # Optional. Limit auto-activation to file patterns
disable-model-invocation: false   # Optional. Prevent auto-invocation
---`}</CommandBlock>

  <div class="grid md:grid-cols-3 gap-4 mt-6">
    <ContentCard icon="mdi:play-circle" iconColor="bg-brand-700" title="Inline Skill">
      No <code>context:</code> or <code>agent:</code>. Runs directly in the user's conversation. Good for most skills.
    </ContentCard>
    <ContentCard icon="mdi:source-fork" iconColor="bg-cyan" title="Forked Skill">
      Uses <code>context: fork</code> + <code>agent:</code>. Creates an isolated subagent. Main context stays clean from large MCP output.
    </ContentCard>
    <ContentCard icon="mdi:sitemap" iconColor="bg-emerald-600" title="Coordinator Skill">
      Uses Task tool in the body. Delegates to executor agents. Should ONLY delegate -- never implement directly.
    </ContentCard>
  </div>

  <HighlightBox severity="warning" title="$ARGUMENTS">
    <code>$ARGUMENTS</code> is replaced with whatever the user typed after the command. Example: <code>/dx-req 2416553</code> sets <code>$ARGUMENTS = "2416553"</code>.
  </HighlightBox>
</Section>

<SectionHeading
  badge="Agents"
  badgeColor="warning"
  title="Agent Authoring"
  subtitle="Define who does the work -- model tier, tools, and permissions."
  bg="alt"
/>
<Section>
  <CommandBlock label="Claude Code agent frontmatter">{`---
name: my-agent
description: What it does
model: sonnet              # sonnet | opus | haiku | inherit
tools: Read, Write, Bash   # OMIT to inherit ALL tools (recommended for MCP)
disallowedTools: Write     # Block specific tools while inheriting rest
permissionMode: default    # default | acceptEdits | bypassPermissions
maxTurns: 30
memory: project            # user | project | local
isolation: worktree        # Isolated git worktree
---`}</CommandBlock>

  <HighlightBox severity="error" title="The #1 Gotcha: Tool Inheritance">
    If you specify <code>tools:</code>, the agent can ONLY use those listed tools. MCP tools are BLOCKED unless explicitly listed. Either <strong>omit tools: entirely</strong> to inherit everything (recommended for MCP-dependent agents), or use <code>disallowedTools:</code> to block specific tools while keeping everything else.
  </HighlightBox>

  <h3 class="text-base font-semibold text-brand-900 mt-6 mb-3">Model Tier Strategy</h3>
  <div class="grid md:grid-cols-3 gap-4">
    <ContentCard
      icon="mdi:star"
      iconColor="bg-red-500"
      title="Opus -- Deep Reasoning"
      tags={[{ label: 'T1', color: 'error' }]}
    >
      Architecture, planning, code review, security analysis, root cause diagnosis. Cost: ≈15x haiku.
    </ContentCard>
    <ContentCard
      icon="mdi:diamond-stone"
      iconColor="bg-amber-500"
      title="Sonnet -- Standard Work"
      tags={[{ label: 'T2', color: 'warning' }]}
    >
      Implementation, MCP coordination, PR review, AEM inspection. Cost: ≈5x haiku.
    </ContentCard>
    <ContentCard
      icon="mdi:circle"
      iconColor="bg-emerald-600"
      title="Haiku -- Fast Ops"
      tags={[{ label: 'T3', color: 'success' }]}
    >
      File lookups, doc search, git commits, config reads. Cost: 1x (baseline).
    </ContentCard>
  </div>

  <HighlightBox severity="info" title="Write the alias, never a pinned model id">
    Use <code>model: opus | sonnet | haiku</code>. An alias follows the current default generation;
    a version-pinned id goes stale the moment a new model ships.
  </HighlightBox>

  <h3 class="text-base font-semibold text-brand-900 mt-6 mb-3">Effort, and when to escalate</h3>
  <p class="text-sm mb-3">
    Tiering applies at two levels: agents set <code>model:</code> in frontmatter, and skills can set
    <code>model:</code> and <code>effort:</code> to run directly without an agent. Opus already runs at
    <code>high</code> effort by default, so every <code>model: opus</code> skill gets deep reasoning
    without setting anything.
  </p>

      </tbody>

  <HighlightBox severity="warning" title="xhigh is not a free upgrade">
    Reach for <code>effort: xhigh</code> only when a step has demonstrably failed at <code>high</code>,
    or when reviewing more than five files of changes. It costs more and runs slower. No skill in the
    repo sets it today, so it has <strong>never been measured against <code>high</code></strong> --
    re-check before assuming an escalation helped.
  </HighlightBox>

  <HighlightBox severity="error" title="effort: was silently ignored before v2.1.267">
    That release (2026-09-09) fixed <code>effort:</code> on custom commands, skills and subagents being
    dropped on models whose default effort is pinned (Opus 4.7, Opus 4.8, Fable 5). Any
    <code>effort:</code> set before it was a no-op on those models, so this tiering is only now
    actually in force. The same release added a <code>maxEffortLevel</code> setting (top-level or
    per-model under <code>modelSettings</code>) that caps effort across every provider -- useful as a
    cost ceiling for <code>dx-automation</code> pipeline runs.
  </HighlightBox>
</Section>

      </tbody>
    </table>

  <HighlightBox severity="error" title="A structural check cannot tell you a script works">
    The <code>validate-&#42;.sh</code> scripts read frontmatter, manifests and counts. They pass happily
    over a script that dies on its first call. Two habits follow: a change to anything under
    <code>data/lib/</code> or <code>skills/&#42;/scripts/</code> needs its suite run, and
    <code>node --check</code> / <code>bash -n</code> are <strong>not</strong> verification -- they parse
    syntax and cannot see a rejected argument, a schema change, or a wrong enum value. Run the thing.
  </HighlightBox>

  <HighlightBox severity="info" title="CI discovers suites, it does not list them">
    <code>validate.yml</code> globs for <code>run-tests.sh</code>, <code>&#42;.test.sh</code> and
    <code>&#42;.test.js</code> under <code>plugins/</code>, so a new suite is picked up with no workflow
    change -- a hardcoded list is how suites go unrun in the first place. The constraint this places on
    a new suite: it must be <strong>hermetic</strong>. No live ADO, AEM or network, and no dependence on
    ambient git config. Existing suites seed throwaway git repos and set <code>user.email</code> /
    <code>user.name</code> per repo; they pass with <code>GIT_CONFIG_GLOBAL=/dev/null</code> and an empty
    <code>HOME</code>. A check that needs a live service belongs in a skill, not a <code>&#42;.test.sh</code>.
  </HighlightBox>

  <h3 class="text-base font-semibold text-brand-900 mt-8 mb-3">Behavioral evals</h3>
  <p class="text-sm mb-3">
    A skill is instructions for a model, so the same prompt can produce different output on different
    runs. An eval scores a skill over repeated runs against a fixture whose correct answer is known in
    advance -- the opposite of an assertion, which expects one exact value. Suites live in
    <code>plugins/&lt;plugin&gt;/evals/</code>.
  </p>

  <CommandBlock label="Run a suite">{`TMPDIR=/tmp claude plugin eval plugins/dx-core --case <case-name> \\
  --runs 3 --ablation none --scaffold --no-publish --allow-tools Write Bash`}</CommandBlock>

  <div class="grid md:grid-cols-2 gap-4 mt-6">
    <ContentCard icon="mdi:target" iconColor="bg-brand-700" title="Fixtures carry a known defect">
      Plus correct distractors -- so graders measure both recall (found the real problem) and precision
      (did not invent others).
    </ContentCard>
    <ContentCard icon="mdi:ruler" iconColor="bg-cyan" title="Prefer deterministic graders">
      Use <code>llm</code> only when no exact oracle exists. <strong>A judge can be argued out of its
      rubric by a confident wrong answer; a regex cannot.</strong>
    </ContentCard>
    <ContentCard icon="mdi:alert-decagram" iconColor="bg-red-500" title="Sanity-check against known-bad input">
      A green suite means either the skill is good or the grader is blind, and you cannot tell which
      until something that should fail does. Each grader needs its own failing case.
    </ContentCard>
    <ContentCard icon="mdi:cash" iconColor="bg-amber-500" title="Cost is real">
      Agent runs are billed; <code>llm</code>/<code>baseline</code> graders add 3 judge calls each, and
      <code>--ablation with-without</code> doubles the run count. Structural graders
      (<code>regex</code>, <code>file_exists</code>, <code>tool_used</code>, <code>tool_order</code>)
      are free. Pilot with <code>--runs 1</code> and cap with <code>--max-cost-usd</code>.
    </ContentCard>
  </div>

  <HighlightBox severity="warning" title="Pin your models before comparing scores">
    Pin <code>--model</code> and <code>--judge-model</code>, or a model rollout reads as a regression.
    <code>TMPDIR=/tmp</code> keeps the sandbox from discovering <code>~/.claude/skills</code>. Do not
    wire evals to every push -- release tags or manual dispatch. Run artifacts land in
    <code>plugins/&#42;/evals/results/</code> and are gitignored.
  </HighlightBox>
