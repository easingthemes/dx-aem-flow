<SectionHeading
  badge="Concept"
  title="What is a Hook?"
  subtitle="A shell script that runs automatically when something happens during an AI session."
  bg="alt"
/>
<Section>
  <ContentCard icon="mdi:webhook" iconColor="bg-brand-700" title="Event-Driven Automation">
    Hooks are like git hooks but for AI sessions. They fire on lifecycle events:
    <ul class="mt-2 list-none p-0 text-sm space-y-1">
      <li><strong>SessionStart</strong> -- when the AI session begins</li>
      <li><strong>PreToolUse</strong> -- before the AI calls a tool (can block it)</li>
      <li><strong>PostToolUse</strong> -- after the AI finishes calling a tool</li>
      <li><strong>SessionEnd</strong> -- when the AI session ends</li>
      <li><strong>PreModelSwitch</strong> / <strong>PostModelSwitch</strong> -- around a model change (Claude Code v2.1.251+; the pre hook can allow, deny, or ask)</li>
    </ul>
  </ContentCard>
</Section>

<SectionHeading
  badge="Examples"
  badgeColor="secondary"
  title="Real Examples from KAI"
  subtitle="Hooks that run in production every day."
  bg="primary"
/>
<Section>
  <div class="grid md:grid-cols-2 gap-4">
    <ContentCard icon="mdi:play-circle" iconColor="bg-emerald-600" title="SessionStart: Environment Validation">
      Validates <code>.ai/config.yaml</code> exists and Node version matches <code>.nvmrc</code>. Fails fast if the environment is misconfigured.
    </ContentCard>
    <ContentCard icon="mdi:cancel" iconColor="bg-red-500" title="PreToolUse: Branch Guard">
      Blocks <code>git commit</code> on protected branches (main, master, development, develop).
      Prevents accidental commits to the wrong branch.
    </ContentCard>
    <ContentCard icon="mdi:camera" iconColor="bg-cyan" title="PostToolUse: Figma Screenshot">
      Automatically saves screenshots from the Figma MCP to disk. Avoids repeated MCP calls
      for the same design during a session.
    </ContentCard>
    <ContentCard icon="mdi:timer" iconColor="bg-cyan-dark" title="PostToolUse: Subagent Log">
      Logs a timestamp every time a subagent completes. Useful for debugging long-running
      autonomous pipelines.
    </ContentCard>
  </div>
</Section>

<SectionHeading
  badge="Format"
  badgeColor="warning"
  title="Hook File Format"
  subtitle="A single hooks.json file defines all hooks for the project."
  bg="alt"
/>
<Section>
  <CommandBlock label="hooks.json (simplified)">{`{
  "hooks": {
    "SessionStart": [{
      "matcher": "",
      "hooks": [{
        "type": "command",
        "command": "bash session-start.sh"
      }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "if": "Bash(git commit*)",
        "command": "bash branch-guard.sh"
      }]
    }]
  }
}`}</CommandBlock>

  <HighlightBox severity="warning" title="No top-level version key in a plugin hooks.json">
    Do <strong>not</strong> add a <code>version</code> field to a plugin's
    <code>hooks/hooks.json</code>. Claude Code's hook schema has no such key and logs
    <code>hooks.json: unknown key "version" ignored</code> at every session start. One copy still
    serves both platforms without it -- Copilot CLI reads that same plugin file.
    <br /><br />
    The exception is the Copilot-only repo-hooks file <code>/dx-init</code> generates at
    <code>.github/hooks/hooks.json</code>, which keeps <code>"version": 1</code> -- a different
    consumer with a different schema. Do not strip the key there.
  </HighlightBox>

  <HighlightBox severity="warning" title="Repo hooks in .github/hooks must be self-contained">
    Copilot sets <code>CLAUDE_PROJECT_DIR</code> for repo hooks but <strong>not</strong>
    <code>PLUGIN_ROOT</code>, <code>COPILOT_PLUGIN_ROOT</code> or <code>CLAUDE_PLUGIN_ROOT</code>
    (checked on Copilot CLI v1.0.109). A repo hook that runs
    <code>bash "$&#123;PLUGIN_ROOT&#125;/hooks/scripts/x.sh"</code> becomes <code>bash /hooks/scripts/x.sh</code>
    and exits 127. Copilot CLI already runs the plugin's own <code>hooks/hooks.json</code> -- from every
    source, with no dedup -- so the repo file exists for the Copilot <strong>cloud coding agent</strong>,
    which ignores plugins. <code>/dx-init</code> therefore installs only two entries there: the inline
    branch guard (exit 2) and the Stop guard via <code>$&#123;CLAUDE_PROJECT_DIR:-$PWD&#125;</code>.
    <br /><br />
    Installs from before November 2026 also carried SessionStart and PostToolUse entries that need a
    plugin root, and some a <code>Bash(git commit*)</code> matcher or <code>exit 1</code>.
    <code>/dx-doctor</code> reports them; <code>/dx-upgrade</code> repairs dx's own entries and leaves
    every other hook in the file alone.
  </HighlightBox>
</Section>

<SectionHeading
  badge="v1.0.11"
  badgeColor="success"
  title="Hook Merging (Copilot CLI v1.0.11+)"
  subtitle="Multiple plugins can contribute hooks without overwriting each other."
  bg="primary"
/>
<Section>
  <div class="grid md:grid-cols-2 gap-4">
    <ContentCard icon="mdi:merge" iconColor="bg-emerald-600" title="Multi-Plugin Hooks">
      Before v1.0.11, if both dx-core and dx-aem defined hooks, one would overwrite the other.
      Now hooks from multiple extensions <strong>merge</strong> -- each plugin contributes its own hooks
      and they all fire correctly.
    </ContentCard>
    <ContentCard icon="mdi:chat-processing" iconColor="bg-cyan" title="SessionStart Context Injection">
      SessionStart hook <code>additionalContext</code> is now injected into the conversation.
      Our <code>session-start.sh</code> and <code>next-step.sh</code> hooks now surface active specs
      and pending steps in Copilot CLI sessions -- previously this context was lost.
    </ContentCard>
  </div>

  <HighlightBox severity="success" title="What This Means for KAI">
    dx-core owns general hooks (branch guard, subagent log, Figma screenshots).
    dx-aem now has its own <code>hooks.json</code> for AEM full-flow hooks (Playwright screenshots, component inspection, editorial capture).
    Both plugins' hooks fire in the same session without conflict.
  </HighlightBox>
</Section>

<SectionHeading
  badge="v2.1.251"
  badgeColor="secondary"
  title="Model-Switch Hooks (Claude Code)"
  subtitle="PreModelSwitch and PostModelSwitch fire around /model, the /config Model row, the model picker, fast mode when it changes the model, and an SDK / IDE / Remote Control set_model. Editing settings.json is not a trigger."
  bg="alt"
/>
<Section>
  <div class="grid md:grid-cols-2 gap-4">
    <ContentCard icon="mdi:swap-horizontal" iconColor="bg-amber-500" title="PreModelSwitch">
      Runs before a switch someone asked for: <code>source</code> is <code>command</code>,
      <code>picker</code> or <code>sdk</code>. Output <code>permissionDecision</code> is
      <code>allow</code>, <code>deny</code> or <code>ask</code> (no <code>defer</code>). A session that
      cannot ask (<code>claude -p</code>, a pipeline) treats <code>ask</code> as a block. It does
      <strong>not</strong> fire on an automatic fallback or a resume, so it cannot keep a pipeline on Opus,
      and the payload carries model IDs only, not effort. Use it to guard interactive and SDK switches.
    </ContentCard>
    <ContentCard icon="mdi:check-decagram" iconColor="bg-emerald-600" title="PostModelSwitch">
      Runs after any switch, including <code>source: auto</code> (fallback) and <code>resume</code>. It
      cannot undo the switch, but <code>hookSpecificOutput.additionalContext</code> reaches the new model,
      so a pipeline can log the model it actually landed on and tell the new model about it.
      Same release: <code>SessionStart</code> on resume also receives how stale the session is and an
      estimated re-cache cost.
    </ContentCard>
  </div>
  <p class="text-sm mt-4">
    Input payload (both events): <code>from_model</code>, <code>to_model</code>, <code>requested_model</code>,
    <code>source</code>, <code>context_tokens</code>, <code>prompt_cache_warm</code>, <code>cache_ttl</code>,
    <code>estimated_cache_write_usd</code>, <code>pricing</code> (read from the v2.1.301 hook schema).
  </p>
  <HighlightBox severity="info" title="Not shipped as a dx-core hook (yet)">
    KAI documents these events but does not install a model-switch guard: a guard in
    <code>dx-core/hooks/hooks.json</code> would fire for every consumer. If one is added it belongs behind
    <code>DX_HOOK_PROFILE=strict</code>. Copilot CLI has no equivalent event.
  </HighlightBox>
</Section>

<SectionHeading
  badge="When to Use"
  badgeColor="info"
  title="When to Use Hooks vs Skills"
  subtitle="Different tools for different jobs."
  bg="primary"
/>
<Section>
  <div class="grid md:grid-cols-2 gap-4">
    <ContentCard icon="mdi:webhook" iconColor="bg-amber-500" title="Hooks">
      <ul class="mt-2 list-none p-0 text-sm space-y-1">
        <li><strong>Automatic</strong> -- fire without user input</li>
        <li><strong>Deterministic</strong> -- shell scripts, no AI reasoning</li>
        <li><strong>Fast</strong> -- milliseconds, no token cost</li>
        <li>Best for: validation gates, caching, logging</li>
      </ul>
    </ContentCard>
    <ContentCard icon="mdi:swap-horizontal" iconColor="bg-brand-700" title="Skills">
      <ul class="mt-2 list-none p-0 text-sm space-y-1">
        <li><strong>Interactive</strong> -- user invokes with /command</li>
        <li><strong>AI-driven</strong> -- reasoning and judgment</li>
        <li><strong>Flexible</strong> -- adapts to context</li>
        <li>Best for: complex tasks, code generation, analysis</li>
      </ul>
    </ContentCard>
  </div>
</Section>

<SectionHeading
  badge="Copilot CLI"
  badgeColor="info"
  title="Hook Limits on Copilot CLI"
  subtitle="Verified on Copilot CLI v1.0.108, except the VS Code note."
  bg="alt"
/>
<Section>
  <HighlightBox severity="warning" title="Guards are best-effort, not a security boundary">
    <ul class="mt-2 list-none p-0 text-sm space-y-1">
      <li><strong>A fourth hook source.</strong> Copilot CLI (v1.0.83+) also runs personal hooks from <code>~/.copilot/hooks/</code>, alongside plugin, <code>.github/hooks</code> and agent hooks, with no dedup. dx ships nothing there.</li>
      <li><strong>Hook fields.</strong> Copilot ignores <code>if</code> (the hook runs on every <code>matcher</code> hit) and <code>async</code> (the hook runs synchronously, and hooks for one event run one after another, so slow hooks add up). <code>timeout</code> is honoured. <code>onFailure</code> has no effect: a <code>preToolUse</code> hook that errors always denies. Verified on v1.0.109.</li>
      <li><strong>Timeouts fail open.</strong> A hook that exceeds its <code>timeoutSec</code> is killed and the tool call is <em>allowed</em>. Keep guards fast and offline (no network calls).</li>
      <li><strong>Stop hooks are capped.</strong> An <code>agentStop</code> hook that blocks is overridden after 8 consecutive blocks; persistence can get past a Stop hook. The dx <code>stop-guard.sh</code> is not affected: Copilot sends <code>stop_hook_active: true</code> on the call after a block, as Claude Code does, and the guard then lets the agent stop (verified on v1.0.109, interactive). As a backup it never blocks the same findings twice in a row.</li>
      <li><strong>Tool name arrives on stdin.</strong> Copilot (and Claude Code) do not set <code>CLAUDE_TOOL_NAME</code>; plugin <code>PostToolUse</code> input provides <code>tool_name</code>. In v1.0.108, file creation and editing both arrived as <code>Edit</code>.</li>
      <li><strong>VS Code Chat (Local agent) ignores <code>matcher</code>.</strong> The agent-scoped branch guard therefore filters on the tool input itself rather than relying on the matcher (from upstream research; not re-run in VS Code).</li>
    </ul>
  </HighlightBox>
</Section>
